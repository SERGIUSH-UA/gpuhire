# Реліз

Коротко: **усе робить `tools/release.py`.** Руками — лише коміт із версією та
журналом змін.

```bash
# 1. один коміт: CHANGELOG.md + src/gpurunner/__init__.py
# 2. запушити його
python tools/release.py check 0.2.5          # нічого не змінює
python tools/release.py cut   0.2.5 --apply  # ворота, public, тег, дзеркало
```

Окремо, і не лише перед релізом:

```bash
python tools/release.py gates                # чи зелене дерево `main`
python tools/release.py gates --ref my-branch
python tools/release.py gates --dirty        # разом зі СВОЇМ незакоміченим
```

🔴 **Повний `pytest` у спільній робочій теці на це питання НЕ відповідає.**
Результат залежить від того, чиї півправки лежать у теці цієї хвилини, і
22.09.2026 це двічі дало фальшивий вирок — в обидва боки: спершу 5 «падінь
релізу», яких у релізі не було, потім чуже падіння на моєму півнаписаному
тесті. `gates` бере дерево з коміта й збирає власне середовище, тож його
відповідь відтворювана й не залежить від сусідньої сесії.

⚠ `--skip-tests` лишає тільки перевірки ФАЙЛІВ (ruff, mypy, приватні дані) —
вони не імпортують пакет, тож середовище їм не потрібне. Про те, що код
робить, такий прогін не каже нічого, і скрипт це друкує вголос.

### `--dirty`: перевірити те, чого ще немає в комітах

Без коміта `gates` вашої роботи не побачить — він бере дерево з `ref`. Щоб
дістати той самий відтворюваний вирок про незакомічене, `--dirty` накладає
зміни робочої теки на зліпок у тимчасовій теці: модифіковані й нові файли
копіюються, видалені — знімаються, перейменовані знімаються за старою назвою.

🔴 **У репозиторій при цьому не пишеться нічого.** Ні `git add`, ні `stash`,
ні власного індексу: у дереві може писати інша сесія, і будь-яка команда, що
чіпає індекс, забрала б її роботу. Файли лише читаються й копіюються;
сторожить `test_dirty_snapshot_is_read_only_for_the_repository`.

⚠ Зліпок містить **усе** незакомічене в теці, зокрема чуже. Це відповідь на
питання «чи зелене те, що я зараз пишу», а не «що поїде в реліз» — скрипт
пише це окремим рядком.

Далі workflow сам: приватні дані → ruff, mypy, pytest → журнал є → колесо,
ім'я й версія якого дорівнюють тегу → смоук у чистому оточенні → PyPI
(Trusted Publishing) → сторінка релізу.

## 1. Чому не можна «просто поставити тег»

Репозиторій **приватний**, а пакет публічний. Між ними стоїть orphan-гілка
`public`: один коміт, чистий корінь, нуль спільної історії з `main`. Історія
розробки заражена від кореневого коміта — пошта автора, шляхи робочих
просторів, прізвище роду, імена приватних проєктів; сторож знаходить у ній
**130 збігів**. Перемикач видимості відкрив би її всю, а не чисте дерево, тому
публікується саме `public`.

Звідси чотири правила. Кожне вже порушувалось руками, і кожне коштувало
окремо — скрипт існує, щоб їх не можна було порушити знову.

### 🔴 Тег ставиться на `public`, ніколи на `main`

`release.yml` тригериться на `tags: ["v*"]`, а ворота приватних даних дивляться
історію **саме тега**. Тег на `main` запускає реліз із приватного дерева:
`scan_private.py --public` там червоний. У найкращому разі це впалий прогін, у
гіршому — спокуса обійти ворота.

`git describe main` при цьому каже «No tags can describe» — і це **не** означає,
що реліз не позначено: з `main` жоден тег не досяжний за побудовою. Перевіряти
`git describe public`.

### 🔴 `public` збирається з дерева коміта, а не з робочої теки

Звичний спосіб — `git checkout --orphan` плюс `git add -A` — забирає в коміт
усе, що лежить у теці. У цьому дереві може писати інша сесія: 21.09.2026 така
спроба **двічі** забрала чужу незакомічену роботу в сусідньому репозиторії, і
двічі її діставали `reset`ом.

Скрипт робить інакше:

```bash
git commit-tree $(git rev-parse main^{tree}) -F <повідомлення>
```

Робочої теки ця команда не читає взагалі. Приймач — порожній
`git diff public main`.

Сторожить `tests/test_release_script.py::test_release_never_touches_the_working_tree`:
він розбирає скрипт по AST і не пускає жодного `git add`, `checkout --orphan`,
`reset --hard`, `stash` чи `clean`.

### 🔴 Ворота ганяються на релізному дереві, а не на робочому

Навіть у worktree з чистого коміта `.venv` головного репо підсовує код через
editable-встановлення: `gpurunner.__file__` вказує в `<репо>/src`. 22.09.2026
це дало «5 падінь релізу», яких у релізі не було — падав незакомічений код
сусідньої сесії.

Скрипт ставить окреме середовище **всередині** worktree (`uv sync` там) і
перевіряє, звідки насправді взято код; якщо з головного репо — зупиняється.

⚠ Тому перед релізом має бути погашений відчеплений наглядач: `uv sync` у
цьому проєкті перезаписує середовище під процесом, який із нього виконується.
Скрипт перевіряє це сам (`tasklist` / `pgrep`).

### 🔴 PyPI не дає правити метадані випущеної версії

Сторінка проєкту бере адреси, опис і класифікатори з **останнього** релізу, а
колесо не видаляється й номер не перевикористовується. Тому всі перевірки
стоять **до** пушу тега.

Наслідок, який уже стався: 0.2.0–0.2.3 назавжди лишаються з посиланнями на
приватний репозиторій, бо помилку знайшли після їх випуску. Виправити можна
було тільки випуском 0.2.4.

## 2. Два імені й два репозиторії

| що | ім'я |
|---|---|
| команда, модуль, змінні оточення | `gpurunner` |
| дистрибутив на PyPI | **`gpuhire`** |
| публічне дзеркало | **`SERGIUSH-UA/gpuhire`** |
| приватний дім розробки | `SERGIUSH-UA/gpurunner` |

`gpurunner` на PyPI зайняв схожий проєкт (`gpu-runner`), і майданчик не дав
його взяти. Перейменували рівно дистрибутив і репозиторій-вітрину; команду —
ні, бо вона стоїть у документації, у скілах Нишпорки й у змінній
`NYSH_GPURUNNER`.

**Дзеркало** містить те саме чисте дерево й ті самі теги. На нього ведуть усі
чотири `project.urls`, тож воно мусить бути живим і актуальним — інакше людина
з PyPI впирається в 404.

🔴 **Actions у дзеркалі мусять бути вимкнені.** Там лежать ті самі workflow'и:
пуш тега запускає другий реліз. 22.09.2026 чотири такі прогони впали з
`invalid-publisher` — PyPI відхилив токен чужого репозиторію. Шкоди не сталось
лише тому, що Trusted Publishing звужений до одного репо. Скрипт перевіряє стан
Actions перед пушем; увімкнути назад — помилка:

```bash
gh api -X PUT repos/SERGIUSH-UA/gpuhire/actions/permissions -F enabled=false
```

## 3. Що перевіряє `check`

| перевірка | чому вона є |
|---|---|
| `__version__` у `<ref>` == версія релізу | читається з **коміта**, не з теки: у теці може лежати півправки |
| `CHANGELOG.md` має `## [X.Y.Z]` | порожня сторінка релізу читається як «нічого не змінилось»; межа розділу обов'язкова, інакше `0.2.1` знайдеться всередині `0.2.10` |
| тега ще немає (локально й в origin) | номер не перевикористовується |
| версії ще немає на PyPI | колесо не видаляється; «спитати не вдалось» показується окремо від «немає» |
| `<ref>` запушено | інакше CI зібрав би інше дерево |
| наглядач не запущений | `uv sync` для воріт перезаписав би середовище під ним |

Брудна робоча тека **не є** перешкодою — про неї лише попереджають, бо в реліз
вона не потрапляє.

## 4. Коли щось пішло не так

**Тег поставлено, а прогін червоний.** Нічого страшного, поки не спрацював
крок PyPI: тег можна зняти (`git tag -d`, `git push origin :refs/tags/vX.Y.Z`),
полагодити, поставити заново. Після успішного PyPI — тільки наступна версія.

**Один тег підняв два прогони.** Дивитись `gh run list`: другий прогін упаде на
PyPI («File already exists») або на Trusted Publishing. Це не пошкодить
випущене.

**Дзеркало відстало.** Безпечно наздогнати вручну:

```bash
git push https://github.com/SERGIUSH-UA/gpuhire.git vX.Y.Z
git push --force https://github.com/SERGIUSH-UA/gpuhire.git public:main
```

**Адреси чи опис на PyPI неправильні.** Тільки наступна версія. Правити
метадані випущеної не можна.

---

## 5. Чого скрипт свідомо не робить

- **Не пише коміт із версією та журналом.** Це зміст, а не механіка: текст
  розділу читає людина зі сторінки релізу.
- **Не переносить сторінку релізу в дзеркало.** `release.yml` створює її в
  приватному репозиторії, бо `GITHUB_TOKEN` звужений до свого репо. Щоб вона
  з'являлась і в дзеркалі, потрібен окремий токен у секретах — рішення власника.
- **Не чистить робочу теку.** Ніколи, за жодних обставин.
